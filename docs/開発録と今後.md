## 1. ひとことで

露出を変えて撮った複数の RAW（AEB ブラケット）を、**RAW のまま** 1 枚の DNG に HDR 合成する macOS アプリ。
書き出した DNG は Lightroom Classic・Camera Raw で普通の RAW と同じように現像でき、レンズプロファイル補正も使える。

| 項目 | 内容 |
|---|---|
| 版 | 1.0.1（2026-10-04 公開） |
| 対応環境 | macOS 10.12.6 以降（Intel）、macOS 11 以降（Apple シリコン）。Universal |
| 言語・構成 | C++17 のエンジン（hdrcore）＋ Objective-C++ / AppKit のアプリ＋ CLI（rawhdr） |
| RAW の読み込み | LibRaw 0.22.2（同梱、LGPL 2.1） |
| ライセンス | GPL 3.0 |
| 配布 | GitHub のリリース（dmg：アプリ・使用説明書・かんたんインストーラ） |
| 規模 | 約 6,600 行（third_party を除く）、自動テスト 50 件 |

### 2.2 合成の考え方（最初に決めたこと）

- **場所ごとに「白飛びしていない中で最も明るいフレーム」を使う**。暗い所はノイズの少ない明るいフレーム、明るい所は白飛びしていない暗いフレームから取る。
  暗いフレームの暗部は使わない。
- **合成は黒を引いた線形の CFA（色補間の前）の値で行う**。色補間・色の変換は Lightroom（または書き出し時のこのアプリ）に任せ、RAW としての調整の余地を最大にする。
- **露出比は EXIF の名目値に頼らず、写真の中身から測る**（隣り合うフレームで両方とも有効な画素から、オフセットつきの頑健な当てはめ）。継ぎ目の段差のいちばんの原因が露出比の誤差だから。
- **飽和レベルは機種の表ではなく、データの中の飽和の山から測る**（ISO によって実際の飽和値が変わるため）。

### 2.3 重要な判断と、検証で分かったこと

開発中に Camera Raw で確かめて分かったことは、次に手を入れる人がつまずきやすい所でもあるので、理由とともに残す。

#### 出力 DNG の形

| 分かったこと | 対応 |
|---|---|
| Camera Raw は浮動小数点の **CFA** DNG を、WhiteLevel を基準におよそ 16 ビット相当で処理する。白から 16 段より暗い所は段差（ポスタリゼーション）になり、WhiteLevel を超える値は切られる | 暗部のノイズと Camera Raw の刻みを比べ、段差が見えるなら **LinearRaw**（このアプリが色補間、Camera Raw は浮動小数点のまま処理）を自動で選ぶ |
| 黒より下のノイズを 0 で切ると暗部の平均が持ち上がり、色かぶりになる | 値を「読み出しノイズの 16 倍」だけ底上げして書き、BlackLevel にその値を書く |
| Camera Raw は BlackLevel を 1/65536 刻みに丸めて引く | 値の倍率を大きく（WhiteLevel 32768／65535）して、底上げを刻みより十分大きくする。BlackLevel は分母 2^30 の有理数で厳密に書く |
| 黒の自動調整（DefaultBlackRender）が HDR の暗部を大きく沈める | DefaultBlackRender = 1（None） |
| 色と明るさが CR2 を開いたときと 0.5 段ほど違う | Adobe DNG Converter で基準フレームを変換し、色の行列・プロファイル・BaselineExposure・ノイズの校正値・レンズ補正の命令を引き継ぐ（テンプレート方式。無ければ LibRaw の値） |
| **「かすみの除去」は WhiteLevel に対する値でかすみの量を見積もるらしい**。最も明るい値が WhiteLevel より 9 段も下にあると全く効かない | LinearRaw では最も明るい値が WhiteLevel の 0.9 倍に来るまで倍率を上げ、BaselineExposure で戻す（1.0.0 で修正） |
| 検証用の XMP に crs:ProcessVersion などが無いと、Camera Raw が露光量などの設定を無視する | 検証では ProcessVersion 15.4・Version 18.6 を必ず入れる（[tools/acr_render.sh](../tools/acr_render.sh)） |

#### 合成と明暗差の圧縮

| 分かったこと | 対応 |
|---|---|
| 重みを空間的な余白（侵食）で切り替えると、小さな明るい物（月）の周りが最も暗い（ノイズの多い）フレームで埋まる | 各ブロック自身の明るさで重みを決め、ぼかしは重みを「上げる」方向だけに使う |
| 明暗差が 14 段を超える場面は、Lightroom の全体のスライダーだけでは仕上げられない（露光量を上げると月が飛び、ハイライト −100 でも戻らない） | **明暗差の圧縮**：バイラテラルグリッドで輪郭を残した大まかな明るさを求め、明るい所・暗い所だけを滑らかな曲線で中間に寄せる倍率をデータに焼き込む（暗室の覆い焼き・焼き込み）。既定 50% |
| 倍率が輪郭で急に変わると、Camera Raw の色補間で縁に色の縞が出る | 圧縮するときは LinearRaw にし、倍率を外してから色補間して掛け直す |
| 月のすぐ外の光のにじみ（月より 6 段暗い）が空の倍率で月より明るくなり、**明るさの順序が逆転**（白い輪と黒い点） | 大まかな明るさから 1 段以上離れた模様を縮める。最も明るい所を場面の中央 +1.5 段より下げない。倍率を画素自身の明るさで読み直す（局所線形モデル） |
| 圧縮後は Lightroom の「色収差を除去」が効かない（縁の明るさの形が変わり「R は G をずらしたもの」が崩れる） | 合成の直後に倍率色収差を自前で補正（R・B を放射方向に拡大縮小。改善が 10% 以上の色だけ） |
| 持ち上げた暗部では NoiseProfile が実際のノイズより小さく、色のノイズ除去が効かず緑の粒が残る | 倍率を考えた代表の倍率 ĝ（暗い側の 97% を覆う最小値）で NoiseProfile を書く |
| 隣どうしの露出比は、どの組も名目値より 1.5〜5% 大きく出る（6D Mark II）。つなぐと積み重なるように見えたが、離れた組をきちんと測ると矛盾は 1% 程度だった。合成と基準フレームの違いは黒のずれ（数 DN）による | 露出比の全体最適化（A4）。離れた組は、暗い方が飽和レベルの 1% 以上の所だけで測る（それより下は黒のずれとノイズで比が大きく狂う） |

#### 開発のやり方

- **Camera Raw での検証を自動化**した（Photoshop の JSX で開いて TIFF に書き出し、数値で比べる）。目で見るだけでなく、色差のばらつき・明るさの比などを測って判断した。
- Photoshop は数十回続けて RAW を開くと「ファイルを開くオプションが正しくない」で開けなくなったり、応答しなくなったりする。書類が無いときだけ再起動して続ける。
- テスト用の写真（柱状節理と月・野島崎灯台、いずれも Canon EOS 6D Mark II）はリポジトリに入れていない（大きく、個人の撮影データのため）。

## 4. 既知の問題

| 問題 | 影響 | 回避策 |
|---|---|---|
| 撮影中に動いたもの（月・雲・波・人）の縁に色の滲み・二重像 | 月の縁にわずかな赤み、動く被写体で目立つ | 手早く撮る。ゴースト対策（§5 提案 A1）が根本解決 |
| 柱状節理の作例で、空が CR2 より 3〜6% 暗い | 原因は露出比のつなぎではなく、短い露出と長い露出の黒のずれ（基準フレームの単位で約 5 DN）。空は基準フレームでは飽和レベルの 0.5〜2% しかないので、数 DN が数 % になる | 実害は小さい。どちらの黒が正しいかは 1 つの作例では決められない（長い露出から来る合成の方が正しい可能性もある）。直すなら各フレームの黒のずれを推定して揃える |
| 明暗差の圧縮 100% は「いかにも HDR」な平坦な見え方になりやすく、暗部のノイズも目立つ | 場面による | 50〜75% を使う |
| 圧縮 0% では「かすみの除去」がほとんど効かない | 月などがとても明るい場面 | 圧縮を使う |
| 公証を受けていないので、初回起動で止められる | 初めての利用者が戸惑う | かんたんインストーラ、使用説明書第 3 章 |
| macOS 10.12 は Xcode 16 の公式な対応範囲の外 | 10.12 の実機で予期しない不具合の可能性 | 実機での確認（§5 提案 C3） |
| 確かめた Camera Raw は 18.6 のみ | 古い Lightroom で見え方が違う可能性 | — |

### 5.2 画質

**A1. ゴースト（動体）対策** — いちばん効果が大きい。

- 露出をそろえたフレーム間の違いを、ノイズモデル（すでに推定している NoiseProfile）から期待されるばらつきと比べ、超える所を「動いた所」とする。
- 動いた所は 1 枚のフレーム（既定は基準、または白飛びしていない最も明るい 1 枚）に固定し、境目は今の重みのぼかしでつなぐ。
- UI では「由来マップ」と同じように動いた所を色で示し、ブラシで足したり消したりできるようにする。
- 月の縁の色の滲み（月の移動）、波・雲・人の二重像がまとめて解決する。

**A2. 回転・1 画素未満の位置合わせ** — 手持ち撮影への対応（計画書 Phase 2 の残り）。

- 推定: 今の平行移動の探索の後に、ECC（相関の最大化）でアフィン変換を求める。
- 出力: 回転が要るときは LinearRaw にする（各フレームを色補間 → 変換 → 合成）。明暗差の圧縮で LinearRaw の書き出しはすでに整っているので、比較的入れやすい。
- 基準フレームは動かさない方針を保ち、無効な端は今と同じく DefaultCrop で隠す。

**A3. 明暗差の圧縮の改良**

- 場面の明暗差（解析の結果に出ている「大まかな明るさの幅」）から、強さの初期値を自動で選ぶ（例: 10 段未満なら 30%、15 段超なら 75%）。
- 「明るい所だけ」「暗い所だけ」を別々に調整できるようにする（今は 1 本のスライダー）。
- 圧縮後の見え方を、プレビューで Camera Raw に近いトーンカーブで再現する（B4 と関係）。

**A4. 露出比の全体最適化**

- **実装済み**。2 枚離れた組の比も測り、すべての組を対数の最小二乗でまとめて解く。残差が 1.5% を超える組は重みを下げる（灯台の波のような動体の組を外すため）。
- 測ってみると、柱状節理の空の暗さ（約 4%）の原因は比のつなぎではなく黒のずれだった（§4）。最適化で比が動いたのは 0.5% 以内。
- 初めは「暗い方がノイズに埋もれた組」も測っていて、灯台ではつなぎ目の比が 4% も動いた。離れた組は暗い方が飽和レベルの 1% 以上の所だけで測る。

**A5. 平均型の合成**

- 白飛びしていないフレームを、ノイズの逆数で重みづけして平均する選択肢。暗部のノイズがさらに減る（ただし動体には弱いので A1 と組み合わせる）。

**A6. X-Trans への対応の仕上げ**

- 富士フイルムの写真で実際に試し、色補間を Markesteijn 法などの高品質なものにする。倍率色収差の補正も X-Trans に広げる。

### 5.3 使い勝手

**B1. 設定の保存とプリセット** — 手間が小さく、毎回の操作が減る。

- 最後に使った設定（圧縮の強さ、書き出し形式など）を NSUserDefaults に保存する。
- 「夕景」「夜景・灯台」「月と地上」などのプリセットを用意する。
- 手動の位置合わせを含む作業内容を、プロジェクトファイル（JSON）として保存・再開できるようにする。

**B2. 処理の進み具合と中止**

- 読み込み・合成・書き出しの各段階に進み具合を通知する仕組みをエンジンに入れ、％の表示と「中止」ボタンを付ける。

**B3. 複数のブラケットの一括処理**

- フォルダを読み込むと、撮影時刻の近さと露出の並び（AEB の枚数・間隔）からブラケットの組を自動で分け、同じ設定で順に書き出す。
- CLI にも同じ機能を付け、大量の写真を処理できるようにする。

**B4. 等倍プレビューと見え方の再現**

- 拡大したときは、元の画素から必要な範囲だけを色補間して表示する（今は長辺 3200 画素に縮小した画像を拡大している）。
- プレビューのトーンを Camera Raw の既定（Adobe Standard のトーンカーブ）に近づけ、「アプリで見た印象」と「Lightroom で開いた印象」の差を小さくする。

**B5. Lightroom Classic との連携**

- Lightroom の「他のツールで編集」から呼べるようにする（選んだ写真を受け取り、合成した DNG を同じフォルダに書く）。
- さらに進めるなら、Lightroom のプラグイン（Lua）から CLI を呼ぶ。

**B6. 英語対応**

- 文字列を Localizable.strings に出し、英語版の説明書を用意する。海外の利用者に広がる。

### 5.4 配布・品質

**C1. Apple の署名・公証**

- Apple Developer Program（年額の費用あり）に登録し、Developer ID で署名して公証を受ける。
- 初回起動の警告が出なくなり、かんたんインストーラの「解除」が不要になる。利用者の不安がいちばん減る。

**C2. CI と Camera Raw の回帰テスト**

- GitHub Actions（macOS）でビルドと自動テストを毎回走らせる。
- Camera Raw での検証（今は手で実行）を、基準の画像と数値（明るさ・色差のばらつき・かすみの除去の効き方など）を保存して比べる形にする。
  明暗差の圧縮のように Camera Raw での見え方が大事な機能を変えるとき、知らないうちに悪くなるのを防げる。

**C3. 他の機種・他の OS での検証**

- Nikon・Sony・富士フイルムなど他のメーカー、別の ISO・レンズの写真で確かめる（とくに飽和レベル・黒レベルの扱い）。
- macOS 10.12・10.13・11・14 の実機または仮想マシンで、起動から書き出しまでを確かめる。計画書 §7.1 のテスト行列を実際に回す。

**A7. Metal による高速化**

- 合成・色補間・バイラテラルグリッドを GPU で行う。今でも 10〜20 秒で目標（10 分以内）を十分満たしているので、優先度は低い。

## 6. 開発を再開するときの手がかり

| 作業 | 手順 |
|---|---|
| ビルド（開発用） | `cmake -S . -B .build/dev -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build .build/dev` |

| 配布用のアプリ | `scripts/build_app.sh`（Universal、最低 OS の確認つき） |
| dmg | `scripts/make_dmg.sh`（アプリ・説明書・インストーラもまとめて作る）。版は `CMakeLists.txt` の 1 か所 |
| 使用説明書 | `docs/manual` で `lualatex manual.tex` を 2 回。画面の撮り直しは `docs/manual/capture.sh` |
| Camera Raw での検証 | `tools/acr_render.sh 入力.dng 出力.tif`（Photoshop 2026 が要る） |
| アプリの自動操作（検証用） | 環境変数 `RBH_OPEN`（開く RAW）・`RBH_VIEW`・`RBH_CHANGE`・`RBH_EXPORT`・`RBH_SNAPSHOT` など（`MainWindowController.mm` の `runAutomationFromEnvironment`） |

コードの入口:

- 合成: `hdrcore/src/merge.cpp`、露出比: `exposure.cpp`、明暗差の圧縮: `tone_compress.cpp`
- DNG の書き出し: `dng_writer.cpp`（底上げ・倍率・NoiseProfile・倍率を画素に配る処理）
- アプリの画面: `app/src/MainWindowController.mm`、プレビュー: `PreviewView.mm`
